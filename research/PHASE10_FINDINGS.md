# A7C II 2.01：MLUT 资源编号来源

延续 [传输描述研究](PHASE9_FINDINGS.md)。本轮确认：七个 MLUT 编号由四个资源槽的占用组合映射而来，不能据此认定有七条独立成像路径。仍未证明静态照片 JPEG 经过该模块。未连接、修改或刷写相机。

## 已验证的规则

CP 函数 `0x54d788` 根据 acquire ID 查表。资源表位于 `0x1a7e578`，四项，每项含两个 32 位字段：owner、type。

- kind=0 时，匹配 owner 且 type=1 的槽。
- kind=1 时，匹配 owner 且 type=2 的槽。
- 其他 kind 不产生匹配。
- 匹配槽组成四位掩码，随后查表得到资源编号。

| 匹配掩码（二进制，低位为槽 0） | 资源编号 / MLUT IP |
| --- | --- |
| 0001 | 0 |
| 0010 | 1 |
| 0100 | 2 |
| 1000 | 3 |
| 1111 | 4 |
| 0011 | 5 |
| 1100 | 6 |

其余组合返回状态 5，不修改输出。后续函数 `0xbb42da` 通过 `0xe9d588` 的七项表做 0–6 恒等映射。

这说明编号可以代表单槽、成对槽或全部槽的组合；尚不知道槽对应的硬件实体、拍摄模式或处理阶段。

## 实际执行的验证

新增 `emulate_mlut_resource_mapping.py`，校验原始 CP 二进制 SHA-256 后执行：

1. `0x54d7c6..0x54d862`：资源匹配原始指令。
2. 手动跳过 OS 解锁与错误处理，执行 `0x54d890..0x54d8d0`：掩码映射。
3. 成功时完整执行 `0xbb42da`：资源编号到 IP 的映射。

资源表为合成输入，不来自真机；未执行锁、分配器、DMA 或拍照。2 种 kind × 16 种掩码，加 3 个类型不匹配/非法 kind 案例，共 **35 组通过**。结果保存于 `a7c2-2.01/cp-mlut-resource-mapping.json`。

两个函数已导出至 `cp-decompiled/`；回归测试同时逐字节核对导出代码与原始固件，当前 **28 项测试通过**。

## 下一步与判断门槛

优先追踪资源表的写入者：`0x54d1a4` 附近存在空闲槽选择，`0x54d338` 附近存在 owner/token 构造。这些目前只是反汇编线索，尚未完成调用链或动态验证。

下一项交付应是“资源申请调用者 → 参数含义 → 静态照片/视频使用场景”的证据链。只有把照片处理调用者与这里的资源组合联系起来，才能评估视频 LUT 模块是否可复用于全分辨率照片。即使映射成立，仍需解决数据格式、下发时序、可执行入口与恢复方案，最终用卡上 JPEG 验证；不是修改一个菜单判断即可完成。
